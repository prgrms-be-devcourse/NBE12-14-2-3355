# 추천 API 부하 테스트 — 실행 스크립트 2개

두 테스트는 같은 시간에 실행하지 않고 하나씩 실행합니다.

| 스크립트 | 대상 API | 시나리오 | 최대 VU 합계 |
|---|---|---|---:|
| `personalized-recommendations.js` | 사용자 맞춤 추천 | `onboarding`, `record` | 10 |
| `related-recommendations.js` | 게임 상세 연관 추천 | `related` | 10 |

테스트 코드는 위 두 JS 파일로 나누고, 공통 실행 도우미 `run.sh`에서
Prometheus 출력과 P95/P99 전송 설정을 자동 적용합니다.
검색 부하 테스트 파일은 별도 기능이므로 유지합니다.

## 1. 준비

백엔드는 localhost:8080, Prometheus는 localhost:9090에서 실행합니다.
백엔드 지표 노출 환경변수는 `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,prometheus`입니다.
모든 명령은 프로젝트 루트에서 실행하세요.
테스트 코드·실행 도우미·로컬 계정 파일은 모두 이 폴더에서 관리합니다. 별도 export는 필요하지 않습니다.

```sh
# k6가 없을 때만 설치
brew install k6

docker compose -f compose.monitoring.yml up -d
```

실행 도우미가 내부 경로를 자동으로 처리하므로 폴더를 이동할 필요가 없습니다.

## 2. 맞춤 추천 실행

```sh
bash k6/recommendations/run.sh personalized
```

- `onboarding`: 온보딩 정보만 있는 고정 계정 5명입니다. 게임 기록은 0개입니다.
- `record`: 게임 기록이 있는 고정 계정 5명이며 **각각 서로 다른 게임 10개**를 COMPLETED로 보유합니다.
- 2026-10-19 로컬 MySQL `gamelog`에 직접 생성했습니다. 기존 개인 계정은 수정하지 않았습니다.
- 온보딩 계정: `k6-onboarding-01@example.com` ~ `k6-onboarding-05@example.com` (user ID 7~11).
- 기록 계정: `k6-record-01@example.com` ~ `k6-record-05@example.com` (user ID 12~16).
- 모든 계정은 USER 권한, 온보딩 완료, 선호 게임 3개·선호 장르 3개를 갖습니다.
  기록 계정의 플레이 기록은 합계 50개이며 리뷰/별점은 추가하지 않았습니다.
- 로그인 정보와 게임 ID는 **Git 제외 파일 `k6/recommendations/.env.recommendation-accounts.json`**에 저장했습니다.
  파일 권한은 600입니다. 비밀번호는 문서·스크립트·Git에 넣지 않습니다.
- 다른 경로의 파일을 쓸 경우 `-e ACCOUNTS_FILE=/절대경로/계정파일.json`을 지정하세요.
- setup에서 기존 계정 10명에 로그인해 토큰을 준비하고, 각 계정의 기록 수/게임 ID/선호 게임과
  추천 결과가 맞는지 검사합니다. 실행할 때 회원가입하거나 선호·플레이 기록을 추가하지 않습니다.
- 두 시나리오는 각각 1 → 3 → 5 → 3 → 1명이며 **합계 2 → 6 → 10 → 6 → 2명**입니다.
  최대 부하에서는 온보딩 사용자 5명, 기록 사용자 5명이 각각 자기 계정으로 요청합니다.
- 이 스크립트는 단일 로컬 k6 프로세스 기준입니다. 각 시나리오의 최대 VU는 5명이며,
  각 그룹에 계정별 슬롯 5개를 만들고 슬롯당 최대 1 VU를 배정합니다.
  전역 VU ID의 나머지 연산은 사용하지 않아 계정이 중복 배정되지 않습니다.
  실행 시나리오 이름은 onboarding_1~5/record_1~5이고 HTTP/check의 scenario 태그는
  기존 Grafana 쿼리에 맞춰 onboarding/record로 유지합니다.

## 3. 게임 상세 연관 추천 실행

맞춤 추천 테스트가 끝난 뒤 실행하세요.

```sh
bash k6/recommendations/run.sh related
```

- `related` 시나리오만 실행합니다. 로그인이나 테스트 계정 생성이 없습니다.
- 기본은 목록 첫 번째 게임입니다. `RELATED_GAME_ID=47808`로 기준 게임을 고정할 수 있습니다.
- `/api/v1/games/{gameId}/related`만 부하 측정합니다. 게임 기본 상세 조회 API 테스트와는 다릅니다.

## 4. 사진과 같은 VU 변화

기본 단계 간격은 15초이며, setup 이후 측정 시간은 105초입니다.
두 스크립트 모두 아래 **합계 VU 목표**를 사용합니다.

| 측정 경과 | 합계 VU 목표 | 동작 |
|---|---:|---|
| 0초 | 2 | 시작 |
| 15초 | 2 | 유지 |
| 30초 | 6 | 증가 |
| 45초 | 6 | 유지 |
| 60초 | 10 | 증가 |
| 75초 | 10 | 유지 |
| 90초 | 6 | 감소 |
| 105초 | 2 | 감소 후 테스트 종료 |

표의 숫자는 단계 끝의 합계 목표입니다. 계정별 1 VU 슬롯이 켜지고 꺼지므로 정수 단위로 변합니다.
마지막에는 테스트가 끝나므로 VU도 종료됩니다.
진행 중인 반복에는 최대 30초의 종료 유예가 있어 실제 표시 시각과 VU가 잠시 차이날 수 있습니다.
반복마다 응답을 받은 뒤 1초 기다립니다. 실제 요청량, 지연 시간, CPU 및 메모리 그래프를
사진의 수치로 고정하지는 않습니다. 해당 수치는 실행 환경과 API 성능에 따라 달라집니다.

`STAGE_DURATION=5s`로 단계 시간을 바꿀 수 있으며, 기본 15초가 예시 사진과 맞습니다.

## 5. 실행 전 자동 검사

setup은 추천 응답이 200이고 목록이 비어 있지 않은지 먼저 검사합니다.
빈 결과라면 맞춤 추천 계정의 선호/기록을 확인하거나 연관 추천의 RELATED_GAME_ID를 선택하세요.
맞춤 추천은 로그인·기존 데이터 검사를 setup에서 수행해 시나리오별 p95/p99 측정에서 제외합니다.
연관 추천 스크립트는 관련 계정/라이브러리/선호 데이터 쓰기 없이 GET만 사용합니다.

## 6. 기존 Grafana 패널

반드시 위 공통 실행 도우미로 실행하세요. `k6 run -o ...`만 직접 실행하면 k6 기본값은
P99만 전송합니다. JS의 `summaryTrendStats`는 터미널 요약 설정이므로 전송 설정을 대신하지 않습니다.
도우미는 기존 환경변수 값과 관계없이 `avg,p(95),p(99)`를 지정하고 native histogram을 꺼서
기존 패널이 조회하는 `_p95`, `_p99` 지표를 함께 전송합니다.
이전 실행에서 누락된 P95는 소급 생성되지 않으므로 수정 후 테스트를 다시 실행하세요.

- Virtual Users: `k6_vus`, 범례 `VUs`.
- 맞춤 추천: `k6_http_req_duration_p95{scenario="onboarding"}`와
  `k6_http_req_duration_p95{scenario="record"}`. 각각 p99도 추가합니다.
- 게임 상세 연관 추천: `k6_http_req_duration_p95{scenario="related"}`와 p99.
- 단위는 seconds(s)입니다. k6 콘솔과 summary JSON의 응답 시간은 ms 단위입니다.
- 기존 Request Rate/Error Rate/CPU/JVM 패널은 서버 지표를 그대로 사용합니다.
- 실행은 하나씩 진행하고 Grafana에서 Last 5 minutes 또는 해당 실행 시간 범위를 선택한 뒤 Refresh하세요.
  별도의 실행 식별 태그는 사용하지 않습니다. 같은 시계열로 이어지므로 다른 실행과 겹친 구간은 해석에 주의하세요.
- p95/p99는 해당 시나리오의 실행 시작 이후 누적 분포이며, 5초 구간의 p95가 아닙니다.
  서로 다른 실행이나 시나리오의 p95를 평균내면 전체 p95가 되지 않습니다.
- 지표 전송 오류도 확인하세요. HTTP 검사 통과만으로 Prometheus 전송 성공을 보장하지 않습니다.
- 필요하면 `--summary-export results/고유한이름.json`을 실행 명령에 추가하세요.
  실행 도우미 내부의 작업 폴더 기준으로 `k6/recommendations/results/`에 저장됩니다.
  Git 제외 경로이며, 프로젝트 루트에서 `mkdir -p k6/recommendations/results`로 만듭니다.

## 7. 측정 시 주의할 점

- 백엔드가 종료/재시작된 실행은 정상 성능 비교에서 제외하세요.
  연결 실패의 응답 시간이 0으로 보인다고 성능이 좋아진 것은 아닙니다.
- 수집·번역·다른 부하 테스트를 함께 실행하지 마세요.
- 전후 비교에는 같은 DB 스냅샷, 게임 ID, JVM/SQL 로그/커넥션 풀 설정을 사용하세요.
  현재 맞춤 추천 스크립트는 준비된 계정/기록을 재사용하지만 로그인 시 인증 토큰 저장은 발생합니다.
- 실패율 1% 미만, 응답 검사 성공률 99% 초과를 검사합니다.
  p99 60초 조건은 요청 제한 수준의 가드이며 성능 목표 달성을 뜻하지 않습니다.

## 기존 통합 버전의 검증 이력

2026-10-19 k6 2.3.0에서 세 추천 경로의 HTTP 200/비어 있지 않은 결과와
Prometheus의 k6_vus 및 onboarding p95 수신을 확인했습니다.
전체 부하 실행은 백엔드 연결 중단으로 완료하지 못했으므로 성능 결과로 사용하지 않습니다.

## 고정 계정 DB 검증 (2026-10-19)

- 온보딩 user ID 7~11: 각각 선호 게임 3개, 선호 장르 3개, 게임 기록 0개.
- 기록 user ID 12~16: 각각 선호 게임 3개, 선호 장르 3개, 게임 기록 10개.
- BCrypt로 비밀번호를 저장하고 동일 인코더의 검증을 통과했습니다.
- 계정 파일의 5+5명, 기록 0/10개, 파일 권한 600, 기본 VU 프로필을 정적으로 확인했습니다.
- 임시 모의 API에 스크립트를 실제 실행해 10개 계정이 각각 사전 확인 1회·측정 1회에
  중복 없이 사용되고 신규 가입/기록 생성 요청이 없는 것을 확인했습니다. 실제 백엔드 성능 검증은 아닙니다.
- 수정한 실행 도우미로 실제 백엔드에서 짧은 동작 검증을 완료했습니다. 맞춤 추천 계정 10명의 로그인·데이터 검사와
  측정 요청 10회(검사 20/20), 연관 추천 측정 1회(검사 2/2)가 통과했습니다.
- 기존 환경에 P99만 지정하고 native histogram을 켜 둔 상태에서도 도우미가 설정을 덮어쓰는 것을 확인했습니다.
  Prometheus에서 onboarding/record/related 각각의 `_p95`, `_p99` 총 6개 시계열 수신을 확인했습니다.
  이 검증은 전송/기능 확인용이며 105초 전체 부하의 성능 측정 결과는 아닙니다.
